业务依据：`../小衣橱_V1_正式PRD_V1.4.md`、`../小衣橱-三子代理公共接口与开发边界说明-V1.md` 及用户最新确认

---

# 1. 文档目的

本文件只定义「衣橱」栏目及其子流程：

```text
我的衣橱主页面
→ 上传新单品
→ AI 识别信息
→ 确认保存
→ 单品详情 / 编辑
→ 删除与历史穿搭兼容
```

开发优先级：

1. 用户确认图片：视觉、布局、卡片形态、页面结构的最高依据。
2. 本开发文档：交互、筛选、视图、字段、删除兼容规则的最高依据。
3. V1.4 正式 PRD：未与前两项冲突的产品总纲继续保留。

禁止子代理擅自：
- 改变图片中的整体视觉风格。
- 新增图片与文档中未定义的大型功能。
- 恢复「配饰」正式分类。
- 把两列网格改回三列。
- 把筛选改成多选。
- 自动生成或猜测购买价格、尺码等无法从图片可靠判断的信息。
- 删除单品后破坏历史已保存穿搭。

---

# 2. 用户需求

衣橱的核心需求：

1. 用户能把自己的衣服快速录入。
2. 用户能通过图片上传 + AI 识别减少手工填写。
3. 用户能按分类、季节、风格、主颜色、厚度快速找到单品。
4. 用户能在手机上舒适查看，因此默认使用两列网格。
5. 用户可切换网格 / 列表视图。
6. 用户能查看、编辑、删除单品。
7. 单品删除后，历史已保存穿搭不能被破坏。
8. 衣橱数据必须同步供「穿搭」栏目使用。

# 24. 删除单品规则

本项目正式采用：

```text
方案 B：删除衣橱单品，但历史穿搭保留快照
```

## 24.1 删除前

必须二次确认。

如果单品正在被历史穿搭引用，可提示：

```text
这件单品已用于历史穿搭。
删除后将不再出现在衣橱和新搭配中，
但历史穿搭仍会保留原来的显示。
```

## 24.2 删除后

单品：

- 从衣橱列表消失。
- 不计入衣橱数量。
- 不参与搜索。
- 不参与筛选。
- 不再出现在穿搭页可选单品中。
- 不再参与「换一套」等新组合逻辑。

## 24.3 历史穿搭

历史已保存穿搭继续保留：

- 当时的单品图片快照。
- 当时的名称。
- 当时的分类。
- 其他必要显示信息。

不得因为衣橱删除而出现：

```text
图片丢失
空白槽位
整套历史穿搭损坏
```

## 24.3.1 云端图片保留规则

删除衣橱单品默认是业务 / 逻辑删除。

如果该单品图片仍被任一历史穿搭快照、今日穿搭或其他正式记录引用：

```text
不得同时物理删除云端图片文件
```

快照应优先保存稳定的 `imageFileId`（或项目现有等价云存储标识）以及展示 URL。

只有确认没有任何正式记录引用时，才允许后续清理云端文件。

## 24.4 加载旧穿搭编辑

如果用户从历史穿搭进入编辑，而其中某件单品已经被删除：

对应槽位显示原快照，并提示：

```text
该单品已从衣橱删除，请重新选择对应单品
```

用户必须重新选择后，才能把该槽位作为新的有效单品继续保存。

# 25. 数据结构建议

单品主数据建议：

```ts
type WardrobeItem = {
  id: string
  createdAt: string
  updatedAt: string

  imageUrl: string
  fileId?: string

  name: string
  category: 'hat' | 'top' | 'bottom' | 'shoes' | 'bag'

  seasons: Array<'spring' | 'summer' | 'autumn' | 'winter'>
  styles: Array<'casual' | 'commute' | 'sweet' | 'cool'>

  primaryColor?: PrimaryColor
  thickness?: 'thin' | 'medium' | 'thick'
  size?: string

  purchasePrice?: number | null
  purchaseDate?: string
  purchaseChannel?: string

  aiDescription?: string
  note?: string

  deletedAt?: string | null
}
```

说明：

- 主颜色为单值 `primaryColor`。
- 季节、风格仍为数组，因为单件衣服可以适合多个季节 / 风格。
- 删除建议使用软删除或等效机制，以便历史穿搭保持引用兼容。
- 如现有工程已有数据结构，优先兼容，不要求为命名统一而破坏旧数据。

# 26. 历史穿搭快照建议

保存穿搭时，每个槽位除 `itemId` 外，应保存必要快照：

```ts
type OutfitItemSnapshot = {
  itemId: string | null

  snapshot?: {
    name: string
    category: string
    imageUrl: string
    imageFileId?: string
    primaryColor?: PrimaryColor
  }
}
```

这样即使原单品之后删除：

```text
历史穿搭仍可正常展示
```

具体字段可结合现有工程调整，但必须满足该业务结果。

# 28. 与穿搭子代理的数据边界

衣橱子代理负责提供：

```text
帽子列表
上衣列表
下装列表
鞋子列表
包包列表
```

每个列表只包含：

```text
当前未删除、可用于新搭配的有效单品
```

穿搭子代理不得读取已删除单品作为新候选。

衣橱发生：

```text
新增
修改
修改分类
删除
```

后，应让穿搭数据源在重新进入或刷新时获得最新结果。

# 29. 与首页子代理的数据边界

首页不直接读取衣橱单品生成推荐。

衣橱只需要保证：

- 单品数据完整。
- 历史穿搭引用兼容。
- 不因单品删除破坏首页最近保存 / 今日穿搭对应的历史缩略图。

# 30. 视觉限制

必须参考用户图片。

保持：

- 粉白背景。
- 粉色主色。
- 大圆角卡片。
- 轻边框。
- 柔和阴影。
- 充足留白。
- 胶囊按钮。
- 标签使用浅粉选中态。

禁止：

- 重新做成深色。
- 改成后台管理系统风格。
- 重新做三列手机网格。
- 把两列卡片压得过小。
- 把筛选改成复杂表单页。
- 大面积增加图片中没有的装饰。

# 32. 验收标准

## 32.1 主页面

- [ ] 页面结构与参考图一致。
- [ ] 手机默认两列网格。
- [ ] 不再使用三列网格。
- [ ] 保留「视图」按钮。
- [ ] 支持两列网格 / 列表切换。
- [ ] 记住用户上一次视图选择。
- [ ] 保留搜索。
- [ ] 保留筛选。
- [ ] 正式分类只有五类。
- [ ] 页面不存在「配饰」正式分类。
- [ ] 单品图片不被裁切。

## 32.2 筛选

- [ ] 只筛季节 / 风格 / 主颜色 / 厚度。
- [ ] 四类筛选目前全部单选。
- [ ] 筛选面板存在「重置 / 查看结果」。
- [ ] 生效后顶部筛选按钮有状态提示。
- [ ] 搜索、分类、筛选可叠加。

## 32.3 上传

- [ ] 上传流程为三步。
- [ ] 支持拍照和相册。
- [ ] 一件单品一张主图。
- [ ] AI 可识别名称 / 分类 / 主颜色 / 季节 / 风格 / 厚度。
- [ ] AI 不编造购买信息和尺码。
- [ ] 识别结果可以修改。
- [ ] 可以重新识别。
- [ ] AI 介绍可编辑、可重新生成。
- [ ] 主颜色字段单选。
- [ ] 必填项未满足不能保存。
- [ ] 所有选填项为空仍可保存。

## 32.4 编辑与删除

- [ ] 修改分类后衣橱立即更新。
- [ ] 修改分类后穿搭数据源同步更新。
- [ ] 删除必须二次确认。
- [ ] 删除后不再参与新搭配。
- [ ] 删除后历史穿搭仍保留原快照。
- [ ] 被历史穿搭引用的云端图片不得随衣橱删除动作物理删除。
- [ ] 加载包含已删除单品的历史搭配时有明确提示。
- [ ] 历史穿搭不会因删除原单品而损坏。

## 32.5 联调

- [ ] 新增单品后穿搭页能读取。
- [ ] 删除单品后穿搭页不再显示。
- [ ] 修改分类后单品进入正确分类。
- [ ] 首页历史穿搭不因衣橱删除而丢图。

搜索与四类单选筛选完整

五类正式分类正确

AI 识别可确认和修改
+
主颜色单选
+
购买信息不由 AI 编造

新增 / 编辑 / 删除正常
